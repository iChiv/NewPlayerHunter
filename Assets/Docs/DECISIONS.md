# 关键决策记录

本文件记录已经确认、会约束后续设计和实现的决定。决定发生变化时，不删除旧条目；将旧状态改为“已替代”，并引用新的决定编号。

## D-001 首发平台与输入

- 日期：2026-08-10
- 状态：已确认
- 决定：首发只开发 Windows，使用 16:9 横屏界面，优先支持鼠标点击和拖拽。
- 影响：M1 不承担移动端适配、手柄导航和多平台发布成本。

## D-002 以周为时间单位

- 日期：2026-08-10
- 状态：已确认
- 决定：游戏按照周推进。玩家完成本周信息收集与球员分配后，在委托界面结束一轮工作。
- 影响：邮件、委托期限、结果、付款和剧情条件统一使用周数表示。

## D-003 球员真实能力永久隐藏

- 日期：2026-08-10
- 状态：已确认
- 决定：玩家永远不能查看球员真实数值，只能通过简历、订阅内容、推荐信息和后续表现进行判断。
- 影响：UI、存档调试工具和结果反馈必须防止意外泄露真实数据。

## D-004 委托支持多人安排

- 日期：2026-08-10
- 状态：已确认
- 决定：球队委托可以需要一人或多人，包括集体试训、多位置招聘和紧急替补。
- 影响：委托由多个槽位组成，提交与结算需要支持部分完成。

## D-005 结果与报酬延迟

- 日期：2026-08-10
- 状态：已确认
- 决定：球员安排后的成绩和工作报酬通常在一到两周后反馈。
- 影响：经济系统必须区分当前现金与应收款；周推进必须处理待结算队列。

## D-006 内容采用虚构喜剧风格

- 日期：2026-08-10
- 状态：已确认
- 决定：角色和球队总体虚构，可以使用足球人物原型和文化梗制造联想，但不完整照搬现实姓名、履历、照片或俱乐部标识。
- 影响：角色美术优先使用原创或风格化生成肖像，笑点来自特征组合、语言和事件结果。

## D-007 文档维护位置

- 日期：2026-08-10
- 状态：已确认
- 决定：项目设计、进度、TODO 和决策记录统一放在 `Assets/Docs`。
- 影响：每个功能交付时同步更新 `PROGRESS.md` 与 `TODO.md`，规则变化同步更新本文件和游戏设计文档。

## D-008 正式场景直接保存玩法对象

- 日期：2026-08-10
- 状态：已确认
- 决定：项目规模较小，直接使用正式 Game.unity 迭代。摄像机、灯光、输入系统、Canvas、顶部栏、委托区、球员卡、招聘槽位、底部反馈区和拖拽提示必须作为场景对象出现在 Hierarchy 中，不在运行时搭建结构。
- 影响：运行时控制器只绑定数据并更新已有 View 的内容、颜色和显隐。M1 使用固定数量的预置 View；如需重建结构，只能显式运行 Editor 场景搭建命令并重新验证。

## D-009 信息筛选是默认工作区

- 日期：2026-08-10
- 状态：已确认
- 决定：每周默认进入邮件/订阅浏览器。玩家通过左上角按钮在信息工作区和球员分配工作区之间切换，先对照有立场的直接邮件与相对独立的订阅报道，再作出安排。
- 影响：信息列表、筛选按钮和正文阅读窗与委托工作台并列存在于正式场景；顶部经济状态和底部反馈跨工作区保持可见。

## D-010 中文优先并保留中英双语结构

- 日期：2026-08-10
- 状态：已确认
- 决定：开发阶段所有玩家可见内容使用中文；静态内容同时保留中文与英文字段，英文缺失时回退中文，后续统一翻译。
- 影响：新增内容必须进入本地化字段，不能再把最终玩家文本硬编码到控制器或场景逻辑中。

## D-011 实际阅读邮件才解锁工作台内容

- 日期：2026-08-10
- 状态：已确认
- 决定：收到邮件不等于已掌握档案。玩家必须点开招聘邮件或球员简历，关联需求或球员才出现在分配工作台；期刊不能替代正式邮件解锁。
- 影响：运行时状态与存档必须记录已读邮件、已解锁需求和已解锁球员的稳定 ID。

## D-012 邮件和期刊采用不同信息结构

- 日期：2026-08-10
- 状态：已确认
- 决定：邮件列表固定显示头像、标题、收件时间、已读标记和正文摘要；邮件正文固定放置需求/价目或球员简历。订阅内容采用可翻页电子期刊，并针对封面、专题和球探报告使用不同排版。
- 影响：邮件与期刊使用独立 Scene View 层级和数据模型，不能用同一种普通消息详情页复用表现。

## D-013 可用球员采用到达顺序的通用列表

- 日期：2026-08-10
- 状态：已确认
- 决定：球员卡不按球员或位置固定；同一位置可有多名球员。已解锁球员按其第一封关联邮件的到达周与周内顺序排列，放入招聘槽位后从可用列表隐藏，撤回后恢复原排序。
- 影响：Scene 只保存固定容量的通用球员卡 View；运行时绑定必须根据当前可用集合重新压紧，存档只保存稳定 ID 和安排状态。

## D-014 人工内容使用标准工作簿提交

- 日期：2026-08-10
- 状态：已确认
- 决定：外部内容人员通过统一 Excel 分表提交球员、招聘、槽位、邮件、期刊期次、期刊页面和附件；开发阶段中文必填、英文可空，内容人员不直接编辑 Unity 资产。
- 影响：整合前必须校验稳定 ID、跨表引用、枚举、显示顺序、隐藏信息边界和附件授权；原始提交文件保留备份后再导入 `GameContentCatalog`。

## D-015 六周采用手工策划的连续测试季

- 日期：2026-08-10
- 状态：已替代，见 D-017
- 决定：正式场景首个测试季固定为六周，每周五封邮件与一期四页期刊；16 名候选、6 个需求和跨周回收共同组成连续体验，不使用临时 Prototype 或纯随机拼装内容。
- 影响：内容稳定 ID、周数和关联顺序需要通过 EditMode 测试；完整规划维护在 `SIX_WEEK_CONTENT_PLAN.md`。

## D-016 原创测试美术使用可替换图集

- 日期：2026-08-10
- 状态：已确认
- 决定：开发阶段的 16 名球员肖像与 6 期期刊封面使用原创生成图集，不含现实人物、徽章、文字或水印；文字继续由 TMP 排版。
- 影响：`GameContentCatalog` 保存图集引用与稳定索引，Scene 预置 `RawImage` 显示区域，后续替换美术不改变邮件、球员或期刊 ID。

## D-017 采用 52 周足球年度，六周内容作为密集开局

- 日期：2026-08-10
- 状态：已确认
- 决定：正式游戏从 2026-07-06 季前训练开始，最多进行 52 个可玩周；前六周保留手工策划的密集招聘与期刊内容，后续以欧洲俱乐部赛季和欧冠式节点邮件提示转会窗、联赛、欧战、淘汰赛、决赛与赛季总结。
- 影响：界面显示明确日期、赛季阶段与 `n/52` 进度；周 52 后锁定继续推进。后续内容扩充应提高第 7–52 周的招聘密度，而不是改变年度边界。

## D-018 已提交球员永久离池，内容按相对有效期到期

- 日期：2026-08-10
- 状态：已确认
- 决定：球员提交并结束本周后默认永久离开可用球员池。球员与招聘使用“从开放周起持续几周”的配置；到期未使用内容从工作台消失，并可发送解释离队、转行或撤单原因的条件邮件。
- 影响：Domain 同时校验同周重复与历史提交，UI 不得只按当前槽位过滤。招聘对玩家显示剩余周数和由日历计算的明确截止日期。

## D-019 足球内容、俱乐部履历与方形美术规范

- 日期：2026-08-10
- 状态：已确认
- 决定：内容只使用足球语汇和欧洲俱乐部赛事节奏。招聘固定提供俱乐部实力、上赛季排名和历史最好成绩；利益请托可以指定目标俱乐部条件。球员肖像、邮件头像和期刊封面统一使用 1:1 方形构图和显示。
- 影响：人工内容模板需要相应字段；Scene 中图片 View 使用 1:1 比例约束；文案与美术检查必须排除美式橄榄球元素。

## D-020 存档快照 schemaVersion 与迁移策略

- 日期：2026-08-19
- 状态：已确认
- 决定：存档快照携带 `schemaVersion`，当前版本为 1。M1 不提供旧版本迁移；加载时版本不匹配即丢弃存档并以新游戏开始，只在 Console 记录警告。后续版本升级时在 Persistence 层追加显式迁移方法，每次只允许逐版本迁移。
- 影响：存档格式变更必须递增版本号并补充版本不匹配测试；不能因为兼容旧档让 Domain 保留废弃字段。

## D-021 随机序列通过种子与消耗次数恢复

- 日期：2026-08-19
- 状态：已确认
- 决定：随机只在提交安排时由 `SeededRandomSource` 消耗。存档保存种子与已消耗次数（draw count），加载后重新构造同源序列并快进到相同位置，不序列化 `System.Random` 内部状态。
- 影响：新增随机消耗点必须仍然经过同一个可计数的 `IRandomSource`；存档往返后相同周的结算结果必须可复现。

## D-022 存档粒度为周初状态，结束本周后自动保存

- 日期：2026-08-19
- 状态：已确认
- 决定：存档记录周开始时的完整进度（当前周、经济、声望、已读/已解锁 ID、提交历史、待结算与待到账、事件标记和日志）；未提交的槽位编辑不入档。每次“结束本周”后自动保存到唯一全局槽位；游戏启动时如果存档存在则恢复，否则新开；“重新开始”删除存档并重置。
- 影响：周中退出最多丢失本周未提交的编辑；自动保存失败不得阻断周推进，只记录错误。

## D-023 Easy Save 3 仅作为键值存储，序列化格式独立于插件

- 日期：2026-08-19
- 状态：已确认
- 决定：Domain 定义纯 C# 快照模型与导出入口，不依赖 Easy Save 或 UnityEngine。Persistence 程序集把快照转换为 JsonUtility 兼容的 JSON 字符串，再经 Easy Save 3 以单个键值写入默认存档文件；Easy Save 3 自带的 asmdef 从 `.disabled` 启用（运行时装配件置于插件根目录，Editor 装配件置于 Editor 目录）。
- 影响：替换或升级存储插件时不改动 Domain；快照往返与版本校验分别在 Domain 与 Persistence 的 EditMode 测试中覆盖。

## D-024 内容批次 01 通过结构化 JSON 管线整合

- 日期：2026-09-07
- 状态：已确认
- 决定：内容人员提交的 Excel 先提取为 JSON 工作副本（`output/spreadsheet/extract_batch.py`），整合者在 `content_design.json` 中补齐稳定 ID、周次、俱乐部、薪资、槽位门槛与图集索引等结构字段，文案补充在独立 prose JSON 中完成，最后由 `build_factory.py` 生成 `LateSeasonContentFactory.cs`；`PopulateM1Defaults()` 合并六周工厂与赛季工厂。批次 01 包含 35 名球员、29 条招聘、64 封解锁邮件与 28 期期刊，排布到第 7–52 周（前密后疏，冬窗与决赛周加密）。
- 影响：新内容不手改 `.asset`；内容变更走"改 JSON → 重新生成"的流水线；结构字段缺省时由整合者按内容规范补齐而非退回。

## D-025 美术图集扩容为 8×8 肖像与 6×6 封面，网格参数常量化

- 日期：2026-09-07
- 状态：已确认
- 决定：球员肖像图集扩为 8×8 @256px（2048²），期刊封面图集扩为 6×6 @256px（1536²）；旧图集单元格按比例裁切保留索引 0–15 / 0–5，新内容由 grok 本地 CLI 生成后经 `rebuild_atlases.py` 合成。`GameController` 的网格参数改为常量 `PlayerAtlasColumns/Rows`、`CoverAtlasColumns/Rows`。
- 影响：新增球员/期刊只分配新索引，不复用旧格；图集变更后必须重跑该脚本并更新索引范围测试。

## D-026 存档兼容延后到游戏完成后统一梳理

- 日期：2026-09-07
- 状态：已确认
- 决定：开发期内存档字段变更直接递增 `schemaVersion` 并丢弃旧档（当前版本 2，新增选中委托 ID）；不再为每个版本写迁移。游戏整体完成后再统一设计存档兼容与迁移方案，届时重写 D-020 的迁移条款。
- 影响：版本不匹配即新开游戏的既有行为保持不变；Persistence 测试只需覆盖当前版本往返与旧版本拒绝。

## D-027 结果邮件叙事变体由既有数据确定性派生

- 日期：2026-09-07
- 状态：已确认
- 决定：试训回函的叙事键在 `placement.accepted/trial_extended/rejected` 基础上扩展变体（意外发挥、性格冲突、体能疑虑、隐藏伤病），由结果类型、匹配分、隐藏体能/职业性与 `randomRoll` 小数分位确定性映射，不新增随机消耗次数；文案选择同样使用 `randomRoll` 质数分位，保证存档恢复后文本一致。
- 影响：D-021 的随机序列恢复策略不受影响；`ResultMailFactory` 以 NarrativeKey 精确匹配优先、旧键回退原有分档文案。
